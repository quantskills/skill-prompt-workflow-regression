# 受限工具入口（本地候选，尚未接入 EVO）

这个入口把“允许读什么”放到模型之外执行。它不是上传到 EVO 后就能自动接管平台权限的 Skill，也不是 Python 沙箱。

## 已实现的边界

- 每轮创建随机会话标识和独立存储目录，目录已存在就停止。
- 输入由可信控制程序提前装载。模型只能用资源编号访问本轮明确提供的文本或表格，不能传入文件路径。
- 表格只能走表格工具，列名和顺序必须与授权定义相同。
- 不提供任意文件读取、脚本执行、联网、委派或回执写入工具。
- 原始请求字节、工具响应和校验链由控制程序独立写入，不接受模型提供的日志替代它们。
- 恢复时检查输入、事件顺序、完成回执和结果是否一致；不完整记录直接停止，不重建或覆盖。
- 回执表示“收到结果，尚未评分”，不表示答案正确。没有平台运行编号就留空，不借用本地主机编号冒充。

实现位于 `scripts/scoped_tools.py`，接口为 `Scope.create`、`Scope.resume`、`Scope.dispatch`。模型只能接触 `dispatch` 的 JSON 输入输出；不能得到 Scope 对象、存储目录或主机执行权限。

```python
from scoped_tools import Scope

# 这些步骤由可信控制程序执行，不由模型生成或调用。
scope = Scope.create('outputs/new-round', {
    'task': {'kind': 'document', 'text': '汇总本轮数量。'},
    'orders': {'kind': 'table', 'columns': ['sku', 'qty'],
               'text': 'sku,qty\nA,3\nB,5\n'},
})
# 将 scope.session_id 和这三个工具的参数规范交给模型：
# read_document(asset), read_table(asset, columns), submit_result(result)。
# 收到模型工具请求后，控制程序组装 session_id、call_id、tool、arguments，
# 转为 UTF-8 JSON 字节后调用 scope.dispatch(raw)。
```

没有模型连接器，不要把示例当作已完成平台集成。模型输出结果的正确性仍需独立评价。

### 本机控制入口

`scripts/local_scope.py` 只在本机工作，不联网、不调用模型。输入文件采用上面示例中的资源字典格式，保存为 UTF-8 JSON。由可信操作者执行：

```powershell
python -X utf8 scripts/local_scope.py init --assets assets.json --directory outputs/new-round
python -X utf8 scripts/local_scope.py verify --directory outputs/new-round
```

调用工具时，可信控制程序把一条 JSON 请求原始字节送入 `call` 的标准输入。请求包含 `session_id`、`call_id`、`tool`、`arguments` 四项。`session_id` 取初始化输出，不从旧任务猜测；`call_id` 使用新的唯一编号。输入来自模型时也只传 JSON，不把内容拼进命令或执行。

```powershell
python -X utf8 scripts/local_scope.py call --directory outputs/new-round
```

`call` 从标准输入读到结束。此入口是开发用控制接口，不是面向普通用户的聊天应用。禁止把 shell、目录参数或本机文件系统访问权交给被测模型，否则它仍可绕过入口。

每次调用是独立进程，启动后重新验证本轮记录。完整调用后进程结束，下次可以恢复；若在写入请求与保存响应之间突然结束，下一次会拒绝恢复，保留残缺原件供核查，不自动编造响应。

## 上线前必须满足

1. 执行宿主关闭全部旁路工具，包括原生读文件、运行代码、联网、委派和写文件。只把受限工具加到原有工具列表不合格。
2. 日志目录位于模型不可访问的宿主侧；输入中不得包含密钥。不能把这套代码放在同一个模型可任意读写的目录里后宣称防篡改。
3. 实际测试尝试读另一轮、任意路径和回执文件，检查宿主拒绝响应；不能用模型自报的“已关闭权限”替代配置事实。
4. 控制程序单进程顺序执行。并发争抢和中断产生不完整记录时停止，由可信操作者核对；不自动修补证据。
5. 平台响应由实际连接器独立保存原始字节，并保留关联标识。当前日志仅是本地工具入口的原件，不是 EVO 原始响应。

`require_restricted_transport` 只做配置完整性检查，不会替平台关闭工具，也不能证明调用者填入的布尔值真实。日志校验链能发现意外修改，但没有外部签名或外部固定校验值，不能抵御掌握宿主磁盘权限的人重写整套记录。

## 2026-11-05 检查结果

新增 24 项本地测试，覆盖跨轮访问、路径输入、工具旁路、列顺序、恢复、重复请求、日志缺失、输入/回执/结果修改和模型伪造回执参数。全仓库共 115 项测试通过。测试先失败再实现，回执恢复校验的漏洞也被新增测试捕获并修正。

EVO 1.1.15 的自定义 Skill 表单只有内容与导入选项；MCP 表单可添加服务、地址与请求头，当前查看的入口未提供关闭原生工具或单任务强制白名单的选项。此前运行审批明确显示无文件隔离。因此尚不能证明该入口在 EVO 中不可绕过，未启动新三轮平台验收，未发布候选。

接入阻塞需要平台支持“只允许指定工具”的执行会话以及独立原始调用记录导出，或经用户确认改用具备该控制能力的执行宿主。不能以新增项目、换模型或删除历史文件代替这一要求。

用户随后限定只使用本机或 EVO，故未接入外部模型服务。另增加三组本机进程级检查，每组都实际启动新进程，依次检查本轮读取、旧会话拒绝、越界路径拒绝、伪造回执请求拒绝、重新启动后读取及回执核对，并模拟记录写到一半时中断。它们是程序测试，不是 Kimi 三轮任务验证。
